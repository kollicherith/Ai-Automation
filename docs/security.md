# Security

What this stack protects, what it doesn't, and where the sharp edges are. Read
the "residual risks" section — it's the honest part.

## What you're defending

An n8n instance holds **credentials to everything it automates**. That is the
real asset. The VM is replaceable; the Google/Slack/Stripe tokens sitting in its
database are not. Two secrets matter most:

| Secret | Where it lives | If it leaks |
|---|---|---|
| `N8N_ENCRYPTION_KEY` | `~/n8n/.env`, and the container's env | Every stored credential is decryptable |
| Backup archives | `~/backups/*.tar.gz.age` | Same, plus the key itself — backups contain both |

Everything below follows from that.

## What's in place

**Network.** In Tailscale mode nothing is open to the internet: n8n binds to
`127.0.0.1:5678` and `tailscale serve` is the only route in. `verify.sh` asserts
it isn't listening on `0.0.0.0` — that check exists because a compose edit could
silently undo it.

**n8n.** Set explicitly in both compose files rather than left to defaults:

- `N8N_BLOCK_ENV_ACCESS_IN_NODE=true` — the important one. Without it a Code node
  can read `process.env`, which is where `N8N_ENCRYPTION_KEY` lives. Anyone who
  can edit a workflow could print your key. Default was `false` before n8n 2.0.
- `N8N_BLOCK_FILE_ACCESS_TO_N8N_FILES=true` — file nodes can't read n8n's own
  config directory, which also holds key material.
- `N8N_RESTRICT_FILE_ACCESS_TO=/files` — file nodes see only the mount. Doubles
  as a fix: n8n 2.x defaults this to `~/.n8n-files`, which would make the `/files`
  mount unreadable to nodes.
- `N8N_PUBLIC_API_DISABLED=true` — nothing here uses the REST API.
- `N8N_SECURE_COOKIE=true` — session cookie over HTTPS only.

**Host.** `harden.sh` installs unattended security upgrades (patches automatic,
reboots manual — an unattended reboot is how an always-on box stops being
always-on), asserts SSH key-only auth with no root login, and adds fail2ban.

**Backups.** Encrypted with `age` to a keypair generated by `harden.sh`, so the
archive is safe to copy off the VM. The backup script **refuses to upload an
unencrypted archive** rather than doing it with a warning.

**Git.** A pre-commit hook blocks `.env`, key files, backup archives,
`launch.json`, and secret-shaped strings (Groq, OpenAI-style, Google, age, OCIDs,
DuckDNS tokens). `stack/scripts/test-git-hooks.sh` proves it still works —
17 cases, both directions. Run it after editing the hook.

## Residual risks

**SSH is still open to the internet.** Oracle's default security list allows TCP
22 from `0.0.0.0/0`. It's the one port this build leaves exposed, and it's the
one that actually gets attacked. On Tailscale you don't need it at all — but
closing it is the single most dangerous step in this whole build, because
getting it wrong locks you out permanently. Confirm `ssh ubuntu@<machine>.ts.net`
works from another device **first**, then remove the rule. `harden.sh --tailscale`
prints this and deliberately does not do it for you.

**The age private key starts on the VM it protects.** `harden.sh` prints it once
and tells you to put it in your password manager. If you skip that and lose the
VM, your off-VM backups are files nobody can open. This is the step people skip.

**Backups are plaintext for a moment.** The archive is built, then encrypted,
then the plaintext is `shred`ed. On the VM's own disk, briefly. Acceptable here;
worth knowing.

**Free LLM tiers see everything you send them.** Most reserve the right to train
on free-tier submissions. This is a data-handling boundary, not a bug: personal
notes fine, anyone else's data not. Moving to a paid tier is partly what buys the
contractual promise not to train on it.

**A workflow can still exfiltrate.** n8n runs arbitrary HTTP requests by design —
that's the product. Blocking env access raises the bar; it doesn't make a
malicious or careless imported workflow safe. Treat community workflow JSON the
way you'd treat a shell script from a stranger.

**Anyone on your tailnet reaches n8n.** Tailscale ACLs default to allow-all
within a tailnet. Fine for a personal account; revisit if you ever add a user.

## Key management, in order

1. **SSH private key** from instance creation — no copy, no VM. Password manager.
2. **`N8N_ENCRYPTION_KEY`** from `~/n8n/.env` — without it, restored credentials
   are unreadable. `deploy.sh` refuses to regenerate it for exactly this reason.
3. **age private key** from `harden.sh` — without it, encrypted backups are junk.

All three in the password manager, today, not "later".

## Restoring

Tested path, on a fresh VM:

```bash
bash scripts/bootstrap.sh --tailscale && newgrp docker
bash scripts/harden.sh --tailscale
# put your age private key at ~/.config/n8n-backup/identity.txt
bash scripts/restore.sh ~/backups/n8n-YYYY-MM-DD.tar.gz.age
```

`restore.sh` decrypts, restores `.env` (and therefore the encryption key), brings
the stack up, and re-imports workflows and credentials. It backs up any existing
`.env` alongside rather than overwriting it.

Afterwards, delete the plaintext exports it left in `~/n8n/files/`.

## If something leaks

1. **Encryption key or a backup** → rotate every credential stored in n8n. The
   key alone is enough to decrypt them. Rotating the key without re-entering
   credentials makes them unreadable, not safe.
2. **A single API key** → revoke at the provider, re-enter in n8n. Groq, Google
   and Cerebras all let you revoke and reissue without touching the account.
3. **Committed to git** → revoke first, then clean history. Deleting the file in
   a later commit does not remove it; anyone with the repo has the old object.
